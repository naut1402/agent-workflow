● Dưới đây là kế hoạch migrate sang Bun + TypeScript. Mình chia theo từng phần
  vì project có 3 mảng riêng (frontend Vue, backend HTTP, MCP server) và mỗi

  Tổng quan: Bun thay được gì?

  │ pnpm install          │ bun install          │ package.json, tạo        │
  │                       │                      │ bun.lockb                │
  ├───────────────────────┼──────────────────────┼──────────────────────────┤
  │ node                  │ bun                  │ Bun chạy TS trực tiếp,   │
  │ server/standalone.js  │ server/standalone.ts │ không cần build/ts-node  │
  ├───────────────────────┼──────────────────────┼──────────────────────────┤

  Điểm mấu chốt: Vite vẫn ở lại. Bun chưa thay được Vite cho Vue SFC (.vue) một
  cách trọn vẹn, nên kiến trúc "một handler, hai transport" của bạn vẫn giữ
  nguyên — chỉ đổi runtime chạy standalone và mcp, và đổi ngôn ngữ file sang
  .ts.

  Việc cần làm

  1. Bootstrap Bun + TS config

  bun install                       # thay pnpm install
  bun add -d typescript @types/node @types/js-yaml vue-tsc
  Tạo tsconfig.json (mode "thoáng" để migrate dần, vì JS hiện tại nhiều any):
  jsonc
  {
    "compilerOptions": {
      "target": "ESNext",
      "module": "ESNext",
      "moduleResolution": "bundler",
      "allowJs": true,            // ⭐ cho phép .js và .ts cùng tồn tại
      "checkJs": false,
      "strict": false,            // bật dần sau
      "noEmit": true,             // Bun/Vite lo transpile, tsc chỉ type-check
      "types": ["bun-types"],
      "skipLibCheck": true,
      "verbatimModuleSyntax": true
    }
  }
  allowJs: true là chìa khóa: bạn migrate từng file một, JS và TS chạy lẫn lộn
  được, không phải đổi hết trong một lần.

  2. Backend server/ — đổi .js → .ts, tận dụng Bun API

  Đây là nơi Bun ăn điểm nhất. server/standalone.js đang dùng node:http + tự
  serve dist/. Bun có Bun.serve() nhanh hơn nhiều và serve static gọn hơn:

  // server/standalone.ts (tùy chọn: dùng Bun.serve thay node:http)
  import { createApiHandler, createRegistryContext } from './devTeamApi.ts'

  const handler = createApiHandler(createRegistryContext())
  Bun.serve({
    hostname: '127.0.0.1', port: 5174,
    async fetch(req) {
      // adapter: handler hiện là (req,res)=>boolean kiểu Node
      // → hoặc viết adapter Request→IncomingMessage, hoặc refactor handler sang
  Web Fetch API
    }
  })
  ⚠️ Đây là quyết định cần cân nhắc: createApiHandler hiện trả về dispatcher
  kiểu Node (req, res) => boolean. Hai lựa chọn:
  - An toàn (khuyến nghị bước 1): giữ node:http — Bun chạy được node:http nguyên
  vẹn. Chỉ đổi đuôi file + thêm type. Zero rủi ro.
  - Tối ưu (bước 2 sau): refactor handler sang Web Request/Response để dùng
  Bun.serve native. Nhưng việc này đụng cả Vite middleware (Vite dùng
  Connect-style (req,res,next)), nên sẽ phá vỡ "một handler hai transport". Mình
  khuyên không làm ở lần migrate đầu.

  Các file cần thêm type: registry.js, devTeamApi.js, knowledge/*.js. Định nghĩa
  vài interface cho ProjectRegistry, PipelineConfig, Catalog, RegistryContext
  để bù phần defensive safeReadDir/statSafe (những hàm này trả union type, type
  lỏng là hợp lý).

  3. MCP server mcp/server.mjs → .ts

  Đơn giản nhất. @modelcontextprotocol/sdk đã có sẵn types. Bun chạy thẳng bun 
  mcp/server.ts. Nhớ cập nhật .claude/settings.local.json nếu nó trỏ tới node 
  mcp/server.mjs → bun mcp/server.ts.

  4. Frontend src/ — Vue + TS (làm sau cùng, tốn công nhất)

  - @vitejs/plugin-vue đã hỗ trợ TS sẵn. Thêm <script setup lang="ts"> vào từng
  .vue dần dần — không cần đổi hết.
  - src/api.js, src/lib/*.js, composables → .ts. agentMarkdown.js được import cả
  ở frontend lẫn backend nên type nó sẽ lợi cả hai phía.
  - Type-check: vue-tsc --noEmit thay cho tsc (vì cần hiểu .vue).
  - index.html đang load /src/main.js → đổi thành /src/main.ts.

  5. Scripts scripts/verify-*.mjs

  Bun chạy Playwright được. Đổi node scripts/verify-x.mjs → bun 
  scripts/verify-x.ts. Đây là phần dễ, ít ràng buộc.

  6. Cập nhật package.json scripts

  jsonc
  "scripts": {
    "dev": "vite",
    "build": "vue-tsc --noEmit && vite build",
    "serve": "bun server/standalone.ts",
    "start": "bun run build && bun server/standalone.ts",
    "mcp": "bun mcp/server.ts",
    "typecheck": "vue-tsc --noEmit"
  }

  Thứ tự đề xuất (rủi ro thấp → cao)

  1. bun install + tsconfig.json với allowJs → mọi thứ vẫn chạy y nguyên bằng
  JS.
  2. MCP server → .ts (độc lập, dễ test bằng bun mcp/server.ts).
  3. server/ backend → .ts, giữ node:http, chỉ thêm type.
  4. scripts/verify-* → .ts.
  5. Frontend src/ → TS dần dần, file nào sửa thì convert file đó.
  6. (Tùy chọn, sau cùng) cân nhắc Bun.serve native — chỉ khi thật sự cần hiệu
  năng.

  Lưu ý / cạm bẫy

  - Vite không biến mất. Bun ≠ Vite. Đừng kỳ vọng thay Vite bằng bun build cho
  Vue — chưa đủ chín.
  - createApiHandler đang là Node-style (req,res) — phải dùng chung cho cả Vite
  middleware lẫn standalone. Đừng đổi sang Web Fetch API nếu vẫn muốn mount vào
  Vite. Đây là ràng buộc kiến trúc quan trọng nhất.
  - Windows: Bun trên Windows đã ổn định nhưng vẫn nên test kỹ phần
  realpathSync/path trong registry.js (validateProjectPath) vì bạn đang chạy
  Win11.
  - bun.lockb là binary — thêm vào git, xóa pnpm-lock.yaml/pnpm-workspace.yaml
  khi đã chắc.

  Bạn muốn mình thực hiện bước 1–2 luôn (bootstrap tsconfig + migrate MCP
  server, ít rủi ro nhất để bạn thấy nó chạy), hay chỉ cần kế hoạch này thôi?

● Câu trả lời ngắn: Bun + TS tương thích tốt với Vercel ở tầng build, nhưng dự 
  án này về bản chất không hợp để deploy backend lên Vercel — và lý do không nằm
  ở Bun/TS, mà ở kiến trúc local-first của chính nó.

  Mình tách 2 vấn đề ra để rõ.

  1. Bun + TS trên Vercel — tương thích đến đâu?

  Tầng: Bun làm package manager
  Tình trạng: ✅ Tốt
  Chi tiết: Vercel tự nhận bun.lockb, chạy bun install ở build step. Ổn định.
  ────────────────────────────────────────
  Tầng: TypeScript
  Tình trạng: ✅ Tốt
  Chi tiết: Vercel transpile TS ngon, không cần cấu hình thêm.
  ────────────────────────────────────────
  Tầng: Bun làm runtime của serverless function
  Tình trạng: ❌ Không
  Chi tiết: Đây là hiểu lầm phổ biến. Vercel không chạy function trên Bun
  runtime
     — function chạy trên Node.js runtime (hoặc Edge). Vercel chỉ dùng  Bun để 
    build, rồi chạy output bằng Node.

  ➡️ Hệ quả thực tế: nếu bước migrate trước bạn dùng Bun.serve(), Bun.file(), 
  Bun.* trong server/, thì chạy local OK nhưng deploy Vercel sẽ chết vì runtime
  là Node, không có global Bun. Đây chính là lý do ở câu trước mình khuyên giữ 
  node:http thay vì chuyển sang Bun.serve. Quyết định đó vô tình giúp bạn tương
  thích Vercel.

  2. Vấn đề lớn hơn: app này là local-first, không phải web app

  Đây mới là điểm cốt lõi. Nhìn lại kiến trúc trong CLAUDE.md:

  - Backend đọc/ghi filesystem vào thư mục .dev-team-agent/ trên máy local của
  user (do orchestrator plugin sở hữu).
  - Registry ở ~/.dev-team-dashboard/projects.json — home directory của máy 
  user.
  - Config CRUD (pipeline, custom-agents, knowledge) ghi file thật xuống đĩa.
  - MCP server là stdio cho Claude Code chạy local.

  Trên Vercel serverless thì:

  ┌─────────────────────────────────────────┬───────────────────────────────┐
  │            Giả định của app             │        Thực tế Vercel         │

  Nói cách khác: kể cả Bun/TS chạy hoàn hảo trên Vercel, API vẫn trả về rỗng vì
  không có dữ liệu nào để đọc. Dashboard này được thiết kế để chạy bên cạnh 
  orchestrator trên cùng một máy — đó là toàn bộ lý do tồn tại của DEV_TEAM_ROOT
  = cwd/...

  Vậy deploy được gì lên Vercel?

  - ✅ Chỉ phần static frontend (dist/ sau vite build) — host được, nhưng nó sẽ
  là cái vỏ rỗng vì backend /api/* không có data.
  - Để frontend-trên-Vercel có ý nghĩa, bạn phải đảo ngược mô hình: từ "đọc
  filesystem local" sang "orchestrator đẩy state lên một database/API ở cloud"
  (Postgres/KV của Vercel, hoặc một backend riêng). Đó là một thay đổi kiến trúc
  lớn, không phải migrate.

  Khuyến nghị

  - Nếu mục tiêu là chạy nội bộ / cá nhân: đừng dùng Vercel. Cứ bun 
  server/standalone.ts (giữ node:http) trên máy local hoặc một VM/Docker có
  quyền đọc thư mục .dev-team-agent/. Đây là cách đúng với thiết kế.
  - Nếu thật sự cần dashboard truy cập qua web cho cả team: deploy standalone
  lên một server/VM bền vững (Fly.io, Railway, VM thường) có filesystem thật +
  mount được workspace, không phải serverless. Vercel-style serverless không phù
  hợp với app đọc/ghi FS.
  - Nếu vẫn muốn Vercel: phải tách thành 2 phần — frontend tĩnh trên Vercel +
  một backend stateful riêng nơi khác, và orchestrator phải đồng bộ state lên
  đó. Cân nhắc kỹ vì công sức lớn.

  Bạn đang nhắm tới kịch bản nào — chạy nội bộ một mình, hay muốn cả team xem
  qua web? Mình tư vấn cụ thể hướng triển khai theo đúng nhu cầu đó.

  Nguyên tắc cốt lõi (đọc trước khi vào plan)

  Bạn nói "TDD để không bị regression" — cần phân biệt 2 thứ, vì áp dụng sai sẽ
  không bảo vệ được:

  1. Migrate/refactor code đã có → không phải TDD thuần (test-first). Code đã
  tồn tại, hành vi đã có. Kỹ thuật đúng là characterization test 
  (golden-master): viết test khóa hành vi hiện tại của JS trước khi đụng vào,
  rồi migrate dưới màu xanh. Test xanh = không regression. Đây là tấm lưới an
  toàn.
  2. Tách module mới / viết logic mới → mới áp dụng test-first TDD thật sự.

  Migration của bạn cần cả hai: lưới an toàn trước, rồi test-first cho phần
  extract.

  Một điểm thuận lợi lớn: Bun có bun test built-in (API tương thích Jest), không
  cần cài thêm runner — đúng tinh thần migrate sang Bun luôn.

  Plan theo phase (rủi ro thấp → cao, mỗi phase commit riêng)

  Phase 0 — Dựng lưới an toàn (chưa đổi 1 dòng code production)

  - tsconfig.json với allowJs: true, strict: false, noEmit: true → JS hiện tại
  vẫn chạy y nguyên.
  - Setup bun test. Viết characterization tests trên code JS hiện có:
    - Unit cho các pure function liệt kê trên (input → output hiện tại, kể cả
  edge case).
    - Round-trip cho agentMarkdown: compile(parse(x)) === x với vài fixture
  thật.
    - Golden/snapshot cho loadPipelineConfig (layered resolution), buildCatalog,
  collectTasks: tạo fixture .dev-team-agent/ tạm trong /tmp, snapshot output
  JSON.
    - API-level (regression mạnh nhất): bật handler, gọi vài route /api/* chính,
  snapshot response. Đây là cái bắt regression khi refactor routing.
  - ✅ Cổng ra: test xanh = "ảnh chụp" hành vi gốc. Từ đây mọi thay đổi phải giữ
  xanh.

  Phase 1 — Bun + TS scaffold, zero behavior change

  - bun install, đổi script sang bun ... (giữ node:http, không dùng Bun.serve —
  để còn deploy được & không phá Vite middleware, như đã bàn).
  - Chạy lại Phase-0 tests bằng bun test → vẫn xanh.

  Phase 2 — Module hóa dưới màu xanh (refactor, không đổi hành vi)

  - Tách từng cụm ra file theo cấu trúc đích, import/export lại, devTeamApi.js
  mỏng dần thành thuần routing.
  - Sau mỗi lần move: chạy test. Đây là lúc lưới an toàn Phase 0 trả công.
  - Làm từng cụm nhỏ một, commit từng cụm.

  Phase 3 — Chuyển JS → TS từng file

  - Đổi .js→.ts, thêm type cho các interface lõi (ProjectRegistry,
  PipelineConfig, CatalogItem, TaskState, RegistryContext).
  - Khi đã có type vững từng module → bật dần strict theo từng folder (strict
  per-file qua // @ts-check hoặc tách tsconfig).
  - Test vẫn là cổng kiểm. File mới tách/sửa logic → test-first (TDD thật).

  Phase 4 — Frontend src/ (làm sau, regression-risk thấp hơn về logic)

  - src/lib/* và src/api.js (pure-ish) → .ts + unit test trước (đặc biệt
  phaseStatus/phasesFromPipeline trong api.js — logic suy diễn, đáng test).
  - .vue → <script setup lang="ts"> dần dần. Component test có thể thêm sau
  (Vitest) nếu cần, nhưng ưu tiên test logic ở lib/ hơn là render.
